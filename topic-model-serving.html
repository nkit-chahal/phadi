Model Serving & Inference

Deploying models at scale with low latency

📌 Serving Options

| Type      | Latency | Use Case                      | Example              |
|-----------|---------|-------------------------------|----------------------|
| Batch     | Hours   | Reports, pre-computed recs    | Nightly predictions  |
| Real-time | <100ms  | Search, fraud detection       | API endpoint         |
| Streaming | Seconds | Event-driven, near real-time  | Kafka + model        |

📖 Serving Patterns

Batch Inference

  • Pre-compute predictions, store in database/cache
  • Good for: Recommendations, reports, scheduled predictions
  • Lower cost, simpler infrastructure

Real-time Inference

  • Compute predictions on-demand via API
  • Good for: Search, fraud, personalization with fresh context
  • Requires low-latency infrastructure

Hybrid (Two-Stage)

  • Stage 1: Batch - generate candidates
  • Stage 2: Real-time - rank with fresh features
  • Common pattern for recommendations at scale

⚡ Optimization Techniques

Model Optimization

  • Quantization: FP32 → INT8, 2-4x faster, minimal accuracy loss
  • Pruning: Remove unnecessary weights
  • Distillation: Train smaller model to mimic larger one
  • ONNX: Convert to optimized runtime format

Infrastructure Optimization

  • GPU serving: NVIDIA Triton, TensorRT
  • Batching: Group requests for GPU efficiency
  • Caching: Store frequent predictions
  • Model replication: Multiple instances behind load balancer

Architecture Patterns

  • Microservices: Separate model from application logic
  • Sidecar: Model container alongside app container
  • Edge deployment: Model on device for ultra-low latency

💻 Code Examples

Python FastAPI Model Serving 
from fastapi import FastAPI
from pydantic import BaseModel
import torch
import time

app = FastAPI()

# Load model once at startup
model = torch.load("model.pt")
model.eval()

class PredictRequest(BaseModel):
    features: list[float]

class PredictResponse(BaseModel):
    prediction: float
    latency_ms: float

@app.post("/predict", response_model=PredictResponse)
async def predict(request: PredictRequest):
    start = time.time()
    
    # Inference
    with torch.no_grad():
        input_tensor = torch.tensor([request.features])
        output = model(input_tensor)
        prediction = output.item()
    
    latency = (time.time() - start) * 1000
    
    return PredictResponse(
        prediction=prediction,
        latency_ms=latency
    )

@app.get("/health")
async def health():
    return {"status": "healthy"}
Python Model Quantization 
import torch

# Dynamic quantization (easiest)
model_fp32 = torch.load("model.pt")
model_int8 = torch.quantization.quantize_dynamic(
    model_fp32,
    {torch.nn.Linear},  # Quantize linear layers
    dtype=torch.qint8
)

# Save quantized model
torch.save(model_int8, "model_quantized.pt")

# Compare sizes
import os
print(f"FP32: {os.path.getsize('model.pt') / 1e6:.1f} MB")
print(f"INT8: {os.path.getsize('model_quantized.pt') / 1e6:.1f} MB")

# Benchmark
import time
def benchmark(model, input_data, n=100):
    model.eval()
    with torch.no_grad():
        start = time.time()
        for _ in range(n):
            _ = model(input_data)
        return (time.time() - start) / n * 1000

print(f"FP32 latency: {benchmark(model_fp32, x):.2f} ms")
print(f"INT8 latency: {benchmark(model_int8, x):.2f} ms")

🎤 Interview Questions & Answers

Q1 How do you reduce model inference latency? +

Answer:

  • Model: Quantization (INT8), pruning, distillation
  • Runtime: ONNX Runtime, TensorRT for GPU
  • Infra: GPU serving, request batching, caching
  • Architecture: Smaller model for initial filter, larger for final

Trade-off: Always benchmark accuracy vs latency impact.

Q2 How do you handle model updates in production? +

Answer:

  • Canary deployment: Route 5% traffic to new model, monitor
  • A/B testing: Random split, measure business metrics
  • Shadow mode: New model runs in parallel, compare outputs
  • Rollback plan: Quick revert if metrics degrade
