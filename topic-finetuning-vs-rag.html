Fine-tuning vs RAG

Choosing the right approach for your LLM application

📌 Quick Decision Guide

┌─────────────────────────────────────────────────────────────┐
│                    CHOOSE RAG WHEN:                          │
│  ✓ Knowledge changes frequently                              │
│  ✓ Need to cite sources                                     │
│  ✓ Limited training data                                    │
│  ✓ Want quick iteration                                     │
│  ✓ Cost-sensitive (no GPU training)                         │
├─────────────────────────────────────────────────────────────┤
│                  CHOOSE FINE-TUNING WHEN:                    │
│  ✓ Need specific output style/format                         │
│  ✓ Domain-specific terminology or behavior                   │
│  ✓ Knowledge is static                                       │
│  ✓ Have lots of training examples                            │
│  ✓ Latency-critical (no retrieval step)                      │
├─────────────────────────────────────────────────────────────┤
│                    OFTEN BEST: COMBINE BOTH                   │
│  Fine-tuned model + RAG for domain style + current knowledge │
└─────────────────────────────────────────────────────────────┘

📖 Detailed Comparison

RAG (Retrieval-Augmented Generation)

✅
Advantages
  • No training required - just index documents
  • Easy to update - add/remove documents anytime
  • Transparent - can cite exact sources
  • Reduces hallucination - grounded in real docs
  • Cost-effective - use off-the-shelf LLM
❌
Limitations
  • Retrieval quality can limit accuracy
  • Added latency from retrieval step
  • Context length limits what can be retrieved
  • Doesn't change model behavior/style

Fine-tuning

✅
Advantages
  • Learns specific output format/style
  • Faster inference (no retrieval)
  • Can learn domain terminology
  • Works for subjective tasks (tone, creativity)
❌
Limitations
  • Requires training data and compute
  • Hard to update - retrain for new info
  • Can increase hallucination if overfitted
  • More expensive and time-consuming
  • Knowledge cutoff remains

📊 Comparison Table

| Aspect           | RAG                    | Fine-tuning            |
|------------------|------------------------|------------------------|
| Setup time       | Hours                  | Days-Weeks             |
| Update knowledge | Add documents          | Retrain                |
| Cost             | Low (inference only)   | High (training+infer)  |
| Latency          | Higher (retrieval)     | Lower (direct)         |
| Hallucination    | Lower (grounded)       | Higher risk            |
| Output style     | Uses base model style  | Customizable           |
| Transparency     | Can cite sources       | Black box              |
| Data needed      | Documents              | Training examples      |

Python Fine-tuning with OpenAI 
import openai
import json

# 1. Prepare training data in JSONL format
training_data = [
    {
        "messages": [
            {"role": "system", "content": "You are a maintenance assistant."},
            {"role": "user", "content": "Motor is overheating"},
            {"role": "assistant", "content": "**Issue:** Motor overheating\n**Likely cause:** Bearing wear or cooling fan failure\n**Action:** Check cooling fan operation, inspect bearings"}
        ]
    },
    # ... more examples (need 10-100+ for good results)
]

# Save as JSONL
with open("training_data.jsonl", "w") as f:
    for example in training_data:
        f.write(json.dumps(example) + "\n")

# 2. Upload file
file = openai.files.create(
    file=open("training_data.jsonl", "rb"),
    purpose="fine-tune"
)

# 3. Create fine-tuning job
job = openai.fine_tuning.jobs.create(
    training_file=file.id,
    model="gpt-3.5-turbo",  # Base model
    hyperparameters={
        "n_epochs": 3
    }
)

# 4. Use fine-tuned model
response = openai.chat.completions.create(
    model="ft:gpt-3.5-turbo:my-org::abc123",  # Fine-tuned model ID
    messages=[
        {"role": "user", "content": "Conveyor belt slipping"}
    ]
)

Python LoRA Fine-tuning (Parameter Efficient) 
from peft import LoraConfig, get_peft_model, TaskType
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from trl import SFTTrainer

# Load base model
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-7b-hf",
    torch_dtype=torch.float16,
    device_map="auto"
)
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-2-7b-hf")

# LoRA config - only train small adapter layers
lora_config = LoraConfig(
    r=16,                # Rank of the update matrices
    lora_alpha=32,       # Scaling factor
    target_modules=["q_proj", "v_proj"],  # Which layers to adapt
    lora_dropout=0.05,
    task_type=TaskType.CAUSAL_LM
)

# Apply LoRA
model = get_peft_model(model, lora_config)
print(f"Trainable params: {model.print_trainable_parameters()}")

🎤 Interview Questions & Answers

Q1 When would you choose RAG over fine-tuning? +

Answer:

Choose RAG when:

  • Knowledge changes: Product catalogs, documentation, news
  • Citations needed: Legal, medical, compliance use cases
  • Quick iteration: Prototype in days/weeks, not months
  • Limited data: Have documents but not training examples
  • Cost constraints: No GPU budget for training
Q2 When is fine-tuning the better choice? +

Answer:

Choose fine-tuning when:

  • Specific output format: JSON structure, report templates
  • Domain style: Legal writing, medical terminology
  • Behavior change: Be more concise, follow specific instructions
  • Latency critical: Can't afford retrieval overhead
  • Knowledge is static: Won't change often
Q3 What is LoRA and why is it popular? +

Answer:

LoRA (Low-Rank Adaptation) is a parameter-efficient fine-tuning method:

  • Only trains small "adapter" layers (~0.1% of parameters)
  • Freezes base model weights
  • Much faster and cheaper than full fine-tuning
  • Can swap adapters for different tasks

Why popular: Makes fine-tuning accessible - can fine-tune 7B model on single GPU.

Q4 Why did you choose RAG for Trident's system? +

Answer (Your Project):

For the breakdown intelligence system, I chose RAG because:

  • Dynamic knowledge: New breakdown reports added daily
  • Citations required: Operators needed to verify suggestions against source incidents
  • No training data: Had documents, not input/output examples
  • Quick deployment: POC needed in 2-3 weeks
  • Reduce hallucination: Safety-critical environment, can't have incorrect instructions

Fine-tuning would help if we needed specific output format - we use prompt engineering instead.
