RAG Architecture

Retrieval-Augmented Generation for grounded LLM responses

📌 Quick Summary

   Documents → Chunking → Embedding → Vector DB
                                          ↓
   Query → Embedding → Similarity Search → Top-K Chunks
                                          ↓
                    Context + Query → LLM → Response
📚
Why RAG?

Ground LLM in external knowledge. Reduces hallucination. Always up-to-date.

🎯
Key Components

Chunking, Embedding, Vector Store, Retrieval, Reranking, Generation

📖 RAG Pipeline Components

1. Document Ingestion & Chunking

  • Why chunk? LLMs have context limits; chunks allow focused retrieval
  • Chunk size: 500-1000 tokens typical, depends on content
  • Overlap: 100-200 tokens to preserve context across boundaries

Chunking strategies:

  • Fixed size: Simple, but may cut mid-sentence
  • Recursive: Split by paragraphs, then sentences if too long
  • Semantic: Group by topic using embeddings
  • Document-aware: Respect headers, sections, tables

2. Embedding

  • Convert text chunks to dense vectors (768-1536 dimensions)
  • Similar meaning → similar vectors → enables semantic search

Popular models:

  • OpenAI ada-002: 1536 dims, great quality, paid
  • Sentence-BERT: Open source, various sizes
  • Cohere Embed: Good multilingual support
  • BGE / E5: Open source, competitive quality

3. Vector Store

  • Store embeddings for fast similarity search
  • Use approximate nearest neighbor (ANN) for speed
  • Options: ChromaDB, Pinecone, FAISS, Weaviate, Qdrant

4. Retrieval

  • Dense retrieval: Embed query, find similar chunks
  • Sparse retrieval: BM25 keyword matching
  • Hybrid: Combine dense + sparse (often best)
  • Top-K: Retrieve 3-10 most relevant chunks

5. Reranking (Optional but Recommended)

  • Rerank retrieved chunks using cross-encoder
  • More accurate than embedding similarity alone
  • Options: Cohere Rerank, sentence-transformers cross-encoders

6. Generation

  • Feed retrieved context + query to LLM
  • Prompt engineering crucial for quality
  • Include instructions to only use provided context

💻 Code Examples

Python Complete RAG Pipeline with LangChain 
from langchain.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import Chroma
from langchain.chat_models import AzureChatOpenAI
from langchain.chains import RetrievalQA

# 1. Load documents
loader = PyPDFLoader("breakdown_manual.pdf")
documents = loader.load()

# 2. Chunk documents
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
    separators=["\n\n", "\n", " ", ""]
)
chunks = text_splitter.split_documents(documents)
print(f"Created {len(chunks)} chunks")

# 3. Create embeddings and store
embeddings = OpenAIEmbeddings()
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="./chroma_db"
)

# 4. Create retriever
retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 5}
)

# 5. Create QA chain
llm = AzureChatOpenAI(
    deployment_name="gpt-4",
    temperature=0
)

qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    chain_type="stuff",  # Stuff all docs into context
    retriever=retriever,
    return_source_documents=True
)

# 6. Query
result = qa_chain({"query": "How to fix motor overheating?"})
print(result["result"])
print(f"Sources: {len(result['source_documents'])}")
Python Hybrid Search (Dense + Sparse) 
from langchain.retrievers import BM25Retriever, EnsembleRetriever

# Dense retriever (semantic)
dense_retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

# Sparse retriever (keyword - BM25)
bm25_retriever = BM25Retriever.from_documents(chunks)
bm25_retriever.k = 5

# Hybrid: combine both with weights
ensemble_retriever = EnsembleRetriever(
    retrievers=[dense_retriever, bm25_retriever],
    weights=[0.6, 0.4]  # 60% semantic, 40% keyword
)

# Use hybrid retriever
docs = ensemble_retriever.get_relevant_documents(
    "motor overheating troubleshooting"
)

# Why hybrid works better:
# - Dense: catches semantic similarity ("hot" matches "overheating")
# - Sparse: catches exact keywords ("motor", "model XYZ123")
Python Reranking for Better Relevance 
from sentence_transformers import CrossEncoder

# Initialize cross-encoder for reranking
reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')

def retrieve_and_rerank(query, retriever, top_k=10, final_k=3):
    """
    Two-stage retrieval:
    1. Get top_k from vector search (fast but approximate)
    2. Rerank with cross-encoder (slow but accurate)
    """
    # Stage 1: Initial retrieval
    docs = retriever.get_relevant_documents(query)[:top_k]
    
    # Stage 2: Rerank
    pairs = [[query, doc.page_content] for doc in docs]
    scores = reranker.predict(pairs)
    
    # Sort by rerank score
    doc_scores = list(zip(docs, scores))
    doc_scores.sort(key=lambda x: x[1], reverse=True)
    
    # Return top final_k
    return [doc for doc, score in doc_scores[:final_k]]

# Usage
reranked_docs = retrieve_and_rerank(
    "How to calibrate the pressure sensor?",
    retriever,
    top_k=10,
    final_k=3
)

🎤 Interview Questions & Answers

Q1 What is RAG and why is it useful? +

Answer:

RAG (Retrieval-Augmented Generation) grounds LLM responses in external knowledge by:

  1. Retrieving relevant documents for a query
  2. Feeding those documents as context to the LLM
  3. Generating response based on retrieved context

Benefits:

  • Reduces hallucination: LLM answers from actual documents
  • Up-to-date: Just update document store, no retraining
  • Transparent: Can cite sources
  • Cost-effective: Cheaper than fine-tuning
Q2 How do you choose chunk size? +

Answer:

Trade-off between context and noise:

  • Too small: Loses context, retrieves incomplete information
  • Too large: Retrieves irrelevant content, wastes tokens

Guidelines:

  • Start with 500-1000 tokens, 10-20% overlap
  • Match chunk size to typical question scope
  • Technical docs: smaller chunks (specific procedures)
  • Narrative: larger chunks (maintain flow)
  • Test empirically: Evaluate retrieval quality at different sizes
Q3 What is hybrid search and why use it? +

Answer:

Hybrid search combines dense (semantic) and sparse (keyword) retrieval:

  • Dense: Understands meaning ("car" matches "automobile")
  • Sparse (BM25): Exact matches (product codes, names)

Why hybrid works better:

  • Dense alone misses exact keyword matches
  • Sparse alone misses semantic similarity
  • Combined: robust across query types

Typical weights: 60-70% dense, 30-40% sparse.

Q4 How do you prevent hallucinations in RAG? +

Answer:

  • Constrain to context: "Only use information from the provided documents"
  • Require citations: Ask LLM to cite sources for each claim
  • Lower temperature: 0-0.3 for factual answers
  • Confidence thresholds: If retrieval scores are low, say "I don't know"
  • Reranking: Ensure retrieved docs are actually relevant
  • Evaluation: Use RAGAS faithfulness metric to measure hallucination
Q5 Describe your RAG implementation at Trident. +

Answer (Your Project):

Problem: Operators spent hours diagnosing machine breakdowns, relying on tribal knowledge.

Solution - RAG over 5 years of breakdown logs:

  • Data: 50K+ breakdown reports (noisy, multilingual)
  • Preprocessing: PII removal, language normalization
  • Chunking: By incident (each breakdown = 1 chunk)
  • Embedding: OpenAI ada-002 via Azure
  • Vector DB: ChromaDB (sufficient scale, easy deployment)
  • Retrieval: Hybrid search (semantic + machine code matching)
  • Generation: GPT-4 with structured output (issue, cause, solution)

Result: 30% reduction in resolution time, operators trust system due to explainable citations.
